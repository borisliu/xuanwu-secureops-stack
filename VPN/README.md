# 企业开源 VPN 产品工程化测试方案

## 1. 测试目标

本项目用于对三款开源/商用友好 VPN 或零信任接入产品进行工程化测试，目标是为企业替代现有硬件 VPN 提供选型依据。

参评产品：

| 产品 | 定位 |
|---|---|
| SoftEther VPN | 最像企业传统 VPN 替代品 |
| OPNsense | 最像下一代安全平台 |
| NetBird | 最像未来零信任网络 |

最终输出：

- 产品部署记录
- 功能测试记录
- 性能测试记录
- 安全测试记录
- 审计能力评估
- 高可用能力评估
- 企业适配度评分
- 最终测试报告

### 3.3 部署形态与工程评价（避免「同一类产品」对比误区）

以下结论与常见部署建议**总体合理**，可作为本测试方案的部署前置共识；同时补充若干工程边界，避免选型时过度简化。

**评价摘要**

| 判断点 | 是否合理 | 说明 |
|--------|----------|------|
| 三者均为 x86 可运行 | 合理 | 客户端与服务器侧均有成熟 x86 路径。 |
| 三者「最佳运行方式」不同 | **合理且关键** | SoftEther 是 Linux 上运行的 **VPN 服务软件**；OPNsense 是 **基于 FreeBSD 的网络操作系统/一体机形态**，不是 `apt install` 型 Linux 应用；NetBird 是 **云原生控制面 + 客户端/中继** 架构，更贴近零信任/Overlay 平台。 |
| SoftEther 优先 Linux VM | 合理 | 不依赖独占网卡或特殊内核，VM 即可覆盖绝大多数企业测试与生产形态；裸机非刚需。 |
| SoftEther 生产慎用 Docker | **大体合理** | TUN/TAP、桥接、与内核网络栈交互使容器化复杂度高；**技术可行**（需 cap、网络命名空间等），适合作为少数团队的 PoC，本方案默认仍以 **裸机或 VM 上原生安装** 为测试基线。 |
| OPNsense 不用 Docker/K8s 承载整机 | 合理 | 应作为 **虚拟机镜像或裸机/工控机** 部署；与「把防火墙当 Linux 应用塞进容器」模型不匹配。 |
| NetBird 优先 Docker Compose / K8s | 合理 | 与自托管管理面、中继的常见实践一致；**补充**：官方亦支持二进制/systemd 等方式，企业可按现有运维标准二选一，测试阶段以 **Compose 或等价编排** 即可。 |
| 三者对标不同商业品类 | 合理 | SoftEther 贴近传统 SSL/IPsec VPN 网关能力；OPNsense 贴近 **NGFW/UTM/边界一体机**；NetBird 贴近 **Tailscale 类 ZTNA/设备网格**。 |
| 第一阶段全部 x86 VM | 合理 | 与本文档测试环境一致；OPNsense 亦无需为 PoC 先上裸机。 |
| 仅 OPNsense「更接近裸机/专用设备」 | **需微调表述** | 裸机/软路由很常见，但 **企业中最常见仍是独立 VM**；裸机更多出于性能、物理端口、故障域隔离，而非「不能用 VM」。 |

**推荐部署方式速查（与测试方案对齐）**

| 产品 | Linux 包安装 | 虚拟机 | 裸机 | Docker/K8s | 本测试方案推荐基线 |
|------|----------------|--------|------|--------------|-------------------|
| SoftEther VPN | 支持（各主流发行版） | 支持 | 支持 | 可行但不作默认生产路径 | **x86 Linux VM + 原生安装**（如 Ubuntu/Debian） |
| OPNsense | 不适用（非 Linux 应用） | **推荐** | 可选 | 不适用整机形态 | **独立 x86 VM**（双网卡/多网段更佳，模拟边界） |
| NetBird | 组件可二进制部署 | 支持 | 支持 | **推荐** | **Docker Compose**（后续可扩展 K8s） |

**与「替换硬件 VPN」的对标关系（便于干系人沟通）**

| 产品 | 更贴近的商业对标 |
|------|-------------------|
| SoftEther VPN | 传统硬件 SSL VPN / 站点与远程接入网关 |
| OPNsense | FortiGate / pfSense / 山石等 **边界安全 + VPN 一体** |
| NetBird | Tailscale、ZTNA、设备与身份驱动的接入 |

**一句话归类（写入测试报告时的定性用语）**

* **SoftEther**：Linux 上的 VPN 服务软件。  
* **OPNsense**：基于 FreeBSD 的网络与安全 **Appliance（网络操作系统）**。  
* **NetBird**：云原生 **零信任/Overlay 接入平台**（控制面 + 数据面组件）。

**虚拟化平台建议**

在 x86 上优先使用 **Proxmox / ESXi / Hyper-V / KVM** 等统一管理多类工作负载（VPN 测试、Wazuh、后续 K8s、实验性 AI Agent 等），与本仓库整体安全运维栈方向一致。

## 6. 三款产品重点测试方向

### 6.1 SoftEther VPN

重点验证：

* 是否适合替代传统硬件 VPN
* Windows 客户端体验
* 固定 IP 分配能力
* 多协议兼容能力
* RADIUS/LDAP 对接能力
* 日志审计能力
* 集群与高可用能力
* 国内复杂网络环境连通性

重点结论：

```text
SoftEther 是否可以作为现有硬件 VPN 的低成本开源替代品？
```

---

### 6.2 OPNsense

重点验证：

* 防火墙 + VPN 一体化能力
* WireGuard / OpenVPN / IPsec 支持情况
* 高可用能力
* 日志与审计能力
* IDS/IPS 能力
* API 与插件扩展能力
* 与现有边界网络融合能力

重点结论：

```text
OPNsense 是否适合作为下一代安全网关平台？
```

---

### 6.3 NetBird

重点验证：

* 零信任 Overlay 网络能力
* OIDC 对接能力
* 用户、设备、资源级策略
* 审计能力
* RDP / SSH / Web 资源访问
* AI Agent / OpenClaw / 运维终端接入能力
* 是否适合未来替代传统 VPN

重点结论：

```text
NetBird 是否适合作为未来零信任接入和 AI 执行层网络？
```

| 固定 IP 能力       |   10 |           |          |         |
| 高可用能力         |   10 |           |          |         |
| 运维复杂度         |   10 |           |          |         |
| 未来扩展能力       |    5 |           |          |         |

评分规则：

```text
5 分：能力完整，企业可直接使用
4 分：能力较强，少量配置或改造可用
3 分：基本可用，但存在明显限制
2 分：能力较弱，需要较大改造
1 分：不适合该场景
0 分：不支持
```

最终得分：

```text
单项得分 = 分值 / 5 * 权重
总分 = 所有单项得分相加
```

## 12. 最终决策原则

如果测试结果显示：

```text
SoftEther 得分最高
```

则建议作为现有硬件 VPN 替代主方案。

如果测试结果显示：

```text
OPNsense 得分最高
```

则建议作为边界安全网关升级方案。

如果测试结果显示：

```text
NetBird 得分最高
```

则建议作为未来零信任接入平台试点方案。

如果三者各有优势，则建议采用：

```text
SoftEther：传统 VPN 替代
OPNsense：边界安全网关
NetBird：零信任与 AI Agent 接入
```

但短期只选择一个主平台时，应优先满足：

```text
稳定替代现有硬件 VPN > 扫码登录扩展 > 审计 > 高可用 > 未来扩展
```
