# ADR-001：DA-SOC v0.1 Hosting Strategy（承载策略、迁移、切换与回退）

| 项 | 内容 |
|---|---|
| **状态** | Accepted（架构委员会裁决） |
| **日期** | V0.1 Architecture Adjudication |
| **决策者** | 玄武云盾 V0.1 架构委员会 |
| **相关** | ADR-003（Harbor）、ADR-004（Storage）、ADR-006（Backup）、ADR-007（Agent Runtime）、ADR-008（Task Model） |
| **取代** | 之前"V0.1 只纳管 ECS / 只做影子环境 / 不迁移 DA-SOC / V0.2 再承载"的全部讨论 |

---

## 1. 决策

> **玄武云盾 V0.1 必须实际承载 DA-SOC v0.1 的完整日常生产链路：`n8n`（编排）+ `da-soc-render`（render + archive）+ `ClickHouse` 全部运行在 Kubernetes `da-soc` Namespace 内，并最终成为唯一的日报生产者。**
>
> 现有 ECS 从"业务承载者"降级为**迁移期数据源与回退保障**，在切换后进入冷备状态，并在 V0.1 结束前完成退役评审。

同时裁定：

1. **切换采用"单写者 + 双读验证"的确定性切换**，而非让两个 n8n 同时产出日报。任何时刻**只有一个日报生产者**。
2. **邮件读取是只读幂等行为**，因此允许迁移期 ECS 与平台两侧读取同一生产邮箱；但**只允许一侧执行完整日报链路**（入库 → 出数 → 出图 → 发送）。
3. **Cutover 必须通过 Cutover Gate（12 项）**，并**预演回退**成功后才能执行。
4. **回退路径必须常备且经过演练**：ECS 保留可运行的镜像、数据与配置至 V0.1 结束。

## 2. 背景

### 2.1 被否决的三个替代方向

| 方向 | 内容 | 否决理由 |
|---|---|---|
| 方向 A：V0.1 只纳管 ECS | Kubernetes 只做管理面/监测，业务仍跑在 ECS Docker | 违背 ADR-001 与 V0.1 核心目标（"第一个可实际承载业务的私有云最小版本"）；无法验证平台承载能力，也无法验证 AI-Native 对业务的可运维性 |
| 方向 B：影子环境 | 平台只做影子运行、不接生产链路 | 影子环境无法暴露真实的网络策略、凭据、调度、时间、DingTalk 通路问题，验收价值接近于零 |
| 方向 C：V0.2 再承载 | V0.1 只建平台，业务留待后续 | 平台会在没有真实业务压力下过度建设（组件堆砌），且 AI Ops 没有真实对象可运维 |

### 2.2 承载不等于忽略迁移风险

"承载 DA-SOC"这一决定本身并不回答"如何安全承载"。DA-SOC 的特殊性在于：

- 它是**每天只有一次机会**的确定性产物（日报图）；
- 它的输入来自**生产邮箱**，且存在**不得 Mark as Read / 不得覆盖指定邮箱**的硬纪律；
- 它的输出发送到**钉钉群**，且生产群与测试群必须严格隔离；
- 它当前运行在 **ECS + Docker + host network** 上，与 Kubernetes 的模型存在真实差异；
- 它有一个**已经确定的业务实现**（SQL 路径 A、n8n 编排权、镜像来源），平台不得为了"架构漂亮"而改变它。

因此本 ADR 的核心不是"要不要承载"，而是：

> **如何在 V0.1 内安全地完成承载，并建立明确的迁移、验证、切换、回退机制。**

## 3. 逐组件部署裁决

裁决原则：**能进 Kubernetes 且不破坏业务语义的，进 Kubernetes；属于生产链路外部依赖或构建期工具的，不进。**

| # | 组件 / 资产 | 裁决 | 部署位置 | 理由 | 风险与对策 |
|---|---|---|---|---|---|
| 1 | **n8n（DA-SOC 日常编排）** | ✅ **进 K8s** | `da-soc` Namespace，Deployment（1 副本）+ PVC 10Gi | 编排权属于 n8n（业务纪律）；必须与 render/archive、ClickHouse 同处一网以便 Service 化；必须被监控与备份 | 复用**现有镜像** `ghcr.io/deluxebear/n8n:chs`，以 digest 固定；不升级版本，避免行为差异。工作流 JSON 只读注入，禁止 UI 改 SQL |
| 2 | **ClickHouse** | ✅ **进 K8s** | `da-soc` Namespace，Deployment（1 副本）+ `local-static` PV 200Gi（Retain），固定节点 | 需长期承载、被监控与备份；host network 必须消除（平台禁 hostNetwork，且 Pod 网络内 Service 访问即可满足） | 监听 8123/9000（非特权端口），去掉 host network；`listen_host` 仅限 Pod 网络；时区显式 `Asia/Shanghai`；单副本单节点 → 明确 RPO=24h（见 §7 与 ADR-004） |
| 3 | **da-soc-render（render + archive）** | ✅ **进 K8s** | `da-soc` Namespace，Deployment（2 副本） | 无状态 HTTP 服务；Service 化后 `n8n → render` 用 ClusterIP，比 host network 更安全可控 | **必须保持"archive 与 render 同镜像同版本"**：同一 Deployment 的同一镜像，禁止分别升级（这是现状隐含约束，必须显式化） |
| 4 | **raw archive（`/data/da-soc/raw`）** | ⚠️ **部分进 K8s** | 保留窗口（≥90 天）落 `da-soc` PVC；**全量历史归档到 K8s 外 MinIO** | 它是邮件原文的落地，是"可重建"的最后依据；但全量历史体积大，不应占用集群 PV | PVC 只保留业务运行所需窗口；全量以不可变对象存 MinIO（见 ADR-006）；迁移时从 ECS 复制 |
| 5 | **SQL（`v0.1/sql/`）** | ✅ **进 Git**，运行时只出现在工作流 JSON 中 | Git 仓库；构建产物进 ConfigMap（只读） | 路径 A：SQL 是**定义**，必须版本化、可评审；运行时不落独立文件避免漂移 | 禁止 n8n UI 修改；每日比对运行中工作流与 Git 产物（配置漂移检测） |
| 6 | **workflow（n8n 工作流 JSON）** | ✅ **进 K8s（只读）** | Git 产物 → ConfigMap/只读卷 → n8n | 编排产物必须与 SQL 一起版本化 | 只读挂载；n8n 不享有持久化写回工作流的权限路径（执行历史走 PVC，工作流定义走只读卷） |
| 7 | **Secrets（IMAP 凭据、DingTalk token 与群 ID、ClickHouse 账号）** | ✅ **进 K8s（加密后进 Git）** | `da-soc` Namespace Secret；Git 中只存**加密形态** | 必须可恢复、可轮换、可审计 | 明文禁止进 Git；使用 Sealed Secrets（或等价方案）使 Git 中仅为密文；群 ID **只能来自 Secret**（业务纪律）；**不覆盖也不持有**「监测bjfz邮箱广电报送信息」相关凭据 |
| 8 | **6 个 Python 脚本 / `run_pipeline.py`** | ❌ **不进 K8s** | 归档到 Git `legacy/` 作为对照 | 业务纪律：日常禁用，编排权归 n8n | 严禁在集群内引入 Python 编排脚本（否则等于绕过 n8n 编排权） |
| 9 | **`tools/build_workflow.py`** | ❌ **不进 K8s** | 构建机（有源码与工具链的环境） | 它是**构建期工具**而非运行期组件 | 产物（工作流 JSON）进 Git 后才可上集群；构建机本身不作为生产依赖 |
| 10 | **镜像构建（da-soc-render:0.1 等）** | ❌ **不进 K8s** | 构建机 → Harbor | 构建与运行分离 | 见 ADR-003/ADR-009 |
| 11 | **邮箱访问（IMAP/POP3）** | ✅ **由 K8s 内 n8n 承担**（迁移后） | `da-soc` n8n 出向 | 平台承载完整链路 | 只读语义、不设 `\Seen`；迁移期两侧可同时只读（见 §5）；未读计数纳入监控 |
| 12 | **DingTalk 发送** | ✅ **由 K8s 内 n8n 承担** | `da-soc` n8n 出向 | 平台承载完整链路 | 群 ID 只来自 Secret；**迁移期平台侧只发测试群**；生产群与测试群严格隔离 |
| 13 | **现有 ECS（ClickHouse/render/n8n）** | ⚠️ **保留但降级** | 迁移期：数据源 + 回退路径；切换后：冷备 | 回退保障必须真实可运行，而非"理论上可以" | 制定退役判据，在 V0.1 结束前做退役决策（见 §9） |

**结论一句话：** 进入 Kubernetes 的是 **n8n + ClickHouse + render/archive**（以及它们的定义与凭据）；不进入的是 **Python 脚本、构建工具、镜像构建**；**raw archive 采用"窗口在集群、全量在对象存储"的分层**；**ECS 保留为回退**。

## 4. Namespace 裁决

| 候选 | 裁决 |
|---|---|
| `da-soc` | ✅ **采用** |
| `da-soc-prod` | ❌ 否决 |

**理由：**

1. V0.1 只有一个 DA-SOC 环境。使用 `da-soc-prod` 会暗示存在 `da-soc-test`/`da-soc-dev` 之类并行环境，而 V0.1 不建设多环境，名称会误导后续的 RBAC/Quota/备份策略设计。
2. 环境的区分应由**集群**承担（V0.1 只有一套集群），而不是由 namespace 后缀承担。未来多环境时，正确做法是 `da-soc`（每集群一套）或引入明确的 `<env>-<app>` 命名约定并由 ADR 重新裁决，而不是在 V0.1 预先猜测。
3. `da-soc` 与业务既有名称（`da-soc-render:0.1`、`/data/da-soc/raw`）一致，减少认知与工具链歧义。

**该 Namespace 必须同时具备：**

| 机制 | 内容 |
|---|---|
| RBAC | 业务主体对该 NS 具备管理权；平台主体只读；Agent 的 executor 仅白名单动词（见 ADR-007） |
| ResourceQuota | CPU/内存/存储/PVC/NodePort=0 等硬上限（防止业务拖垮平台） |
| LimitRange | 默认 request/limit，避免无限制 Pod |
| NetworkPolicy | default-deny + 显式放行清单（见 §6） |
| Pod Security | `restricted`（业务容器均可满足：非 root、无特权、无 hostPath） |
| Secret | 邮箱与 DingTalk 凭据；仅 n8n Pod 可挂载 |
| Storage | `local-static`（ClickHouse，Retain）+ `local-path`（n8n） |
| Service | `clickhouse:8123/9000`、`da-soc-render:8091`、`n8n:5678`（均 ClusterIP） |
| Ingress | **V0.1 不建立业务 Ingress**（无外部用户访问需求）；仅平台管理面使用 Ingress |
| Audit | 该 NS 的所有 apiserver 请求进入 Kubernetes Audit → 集中日志 |

## 5. 网络模型裁决（Kubernetes 化后的确定性链路）

### 5.1 目标链路

```text
                         ┌──────────────── Namespace: da-soc ────────────────┐
  IMAP:993 (出向,只读)   │                                                    │
        ┌────────────────┤  n8n (Deployment)                                  │
        │                │    │  ClusterIP http://da-soc-render:8091          │
        ▼                │    ▼                                               │
  邮箱服务器             │  da-soc-render (Deployment, 2 副本)                 │
                         │    │  ClusterIP http://clickhouse:8123  (HTTP SQL) │
  DingTalk API (出向)    │    ▼                                               │
        ▲                │  ClickHouse (Deployment + local PV)                 │
        └────────────────┤    │  BACKUP → s3://… (MinIO, 集群外)              │
  钉钉群(测试/生产,凭据) │                                                    │
                         └────────────────────────────────────────────────────┘
```

### 5.2 逐项验证要求（不得因 Kubernetes 化而破坏确定性）

| 环节 | Kubernetes 化方式 | 必须验证 |
|---|---|---|
| 邮箱访问 | n8n Pod 出向 `993/TCP`（只读 IMAP，不设 `\Seen`） | ① 同一邮箱、同一过滤条件（From 含 `10099.com.cn` 且主题含「码号处置情况」）拉到同一封邮件集合；② 拉取前后**未读计数不变**；③ 不产生任何写/删除/Mark Read 行为；④ 不对「监测bjfz邮箱广电报送信息」发生任何操作 |
| DingTalk | n8n Pod 出向 `443/TCP`，POC-06A/06C Native API，群 ID 来自 Secret | ① 测试群收到图；② 生产群在迁移期**收不到**平台消息；③ 群 ID 不出现在日志、工作流 JSON、ConfigMap 中 |
| HTTP SQL | n8n → `http://clickhouse:8123`（ClusterIP） | 结果集与 ECS 同 SQL 完全一致（含排序、空值语义） |
| `/archive` | n8n → `http://da-soc-render:8091/archive` | 成功/失败语义与 ECS 一致；失败时**不入库、不出图、不发送** |
| `/render` | n8n → `http://da-soc-render:8091/render` | 出图与 ECS 逐像素/逐字段一致 |
| 时间 | 节点 chrony + 容器显式 `TZ` + ClickHouse `timezone` | 6 周 / 6 月 / 当天三窗口的**边界日**结果与 ECS 一致 |
| host network 消除 | 所有业务 Pod 使用 Pod 网络 + ClusterIP | 节点网段无法直接访问 `8123`/`8091`；无 NodePort；无 hostNetwork |
| DingTalk 回调（入向） | V0.1 采用**出向轮询**为主，不做公网入向 | 审批与查询通过 n8n 定时出向拉取实现；若未来必须回调，另立 ADR 并加白名单与签名 |

### 5.3 NetworkPolicy（业务 NS：default-deny + 白名单）

| # | 方向 | 源/目的 | 端口 | 用途 |
|---|---|---|---|---|
| 1 | Egress | CoreDNS (`kube-system`) | 53 | 域名解析 |
| 2 | Ingress | `da-soc/n8n` → `da-soc-render` | 8091 | `/archive`、`/render` |
| 3 | Ingress | `da-soc/n8n` → `da-soc/clickhouse` | 8123, 9000 | HTTP SQL 查询与写入 |
| 4 | Ingress | 监控抓取（Prometheus）→ `da-soc` | metrics 端口 | 指标采集 |
| 5 | Egress | `da-soc/n8n` → 邮箱服务器 IP | 993 | IMAP（只读，不标已读） |
| 6 | Egress | `da-soc/n8n` → DingTalk API | 443 | POC-06A/06C 发送 |
| 7 | Egress | `da-soc/clickhouse` → MinIO（集群外） | 9000 | `BACKUP` |
| 8 | Egress（**仅迁移期**） | `da-soc/migration-job` → ECS ClickHouse | 8123 | 历史数据只读回补；**迁移完成后立即删除该策略** |

**禁止：** 任何 `da-soc` Pod 与 `aiops`/平台 NS 的未列明互通；任何 NodePort；任何 host network。

## 6. 硬业务规则的平台侧落实（不可改变）

| # | 业务规则 | 平台侧强制手段 | 验证方式 |
|---|---|---|---|
| 1 | **数字只能来自 ClickHouse SQL** | Agent/平台无任何"补数/改数"路径；SQL 仅来自 Git | 审计：`aiops` SA 对 ClickHouse 的写请求计数必须为 0 |
| 2 | **图片只能由 render 生成** | 出图链路唯一；无 LLM 出图通路 | 工作流定义审查 + 产物来源可追溯 |
| 3 | **LLM 不参与出数出图** | ① Agent SA 无 ClickHouse 写权限、无工作流修改权、无钉钉发送权；② ClickHouse 账号分离（writer / read-only）；③ 网络策略不允许 `aiops → da-soc` 写语义 | DB 账号权限导出 + Agent Job 权限清单 + 审计 |
| 4 | **null / 暂无数据不得填 0** | 平台不得引入任何自动补值逻辑；空值语义由业务保留 | 双跑期以"无数据日"或空窗口样例专项验证 |
| 5 | **archive 失败 → 不入库 / 不出图 / 不发送** | 平台不提供绕过失败 archive 直接跑 render/发送的通路；监控显式检测该中止语义 | 人为制造 archive 失败，确认全链路中止 |
| 6 | **不得 Mark as Read / 删除 / 修改生产邮件** | n8n 只读配置；无 SMTP/写协议出向；未读计数监控 | 拉取前后未读计数一致；邮箱侧审计 |
| 7 | **不得覆盖「监测bjfz邮箱广电报送信息」** | 集群内无该邮箱凭据、无写通路 | 审计：对该邮箱的任何写尝试 |
| 8 | **生产群与测试群严格隔离** | 群 ID 只来自 Secret；迁移期平台侧 Secret 中只配置**测试群** | 生产群在迁移期收不到平台消息 |

## 7. 迁移方案（10 阶段）

| Phase | 名称 | 关键动作 | 产物 / 门禁 |
|---|---|---|---|
| **P1** | 建立 K8s 环境 | 平台集群、Calico、存储、Harbor、可观测、备份、RBAC/Quota/NetPol 就绪 | 平台验收通过；**此阶段不触碰 ECS** |
| **P2** | 镜像进入 Harbor | `da-soc-render:0.1`、`clickhouse/clickhouse-server`、`ghcr.io/deluxebear/n8n:chs` 从构建机 `docker save` → 导入 → push 到 Harbor，**记录 digest 并写入版本矩阵** | 三个镜像 digest 与 ECS 运行镜像**逐一比对一致** |
| **P3** | 部署三组件 | ClickHouse（空库 + 与 ECS 一致 schema）→ da-soc-render → n8n（工作流只读注入） | Pod Ready；健康检查通过；期间**不接生产数据** |
| **P4** | 导入历史数据 | ① 从 ECS 以只读方式导出 ClickHouse 数据（临时 NetPol 放行）；② 导入集群 ClickHouse；③ 从 ECS 复制 raw archive 至 PVC 与 MinIO | **Data Parity Report**：`count(*)` 与关键聚合（当天/6 周/6 月）与 ECS **完全一致** |
| **P5** | 导入 workflow | 由 `build_workflow.py` 生成的 JSON 入 Git → ConfigMap → n8n 只读加载；核对 SQL 与 `v0.1/sql/` 源文件一致 | 运行中工作流 = Git 产物（逐字段比对） |
| **P6** | 数据验证 | 三窗口（当天 / 近 6 周 / 近 6 月）在集群侧独立出数，与 ECS 结果逐项比对 | 三窗口全部一致；空值语义正确（无数据不为 0） |
| **P7** | 图片验证 | 集群 render 出图，与 ECS 出图逐项/逐像素比对 | 图片一致（内容、字段、时间标注） |
| **P8** | DingTalk 验证 | 集群 n8n 发送到**测试群**；核对群 ID 来源为 Secret；核对生产群未收到 | 测试群收到；生产群零污染 |
| **P9** | 切换生产入口 | 执行 Cutover Gate → 单写者切换（见 §8） | 切换后首个完整日报由集群产出且数字正确 |
| **P10** | 保留 ECS 回退能力 | ECS 进入冷备：保留镜像、数据、配置；停用其调度；编写并**演练**回退 Runbook | 回退演练在 **30 分钟内**完成并验证 |

### 7.1 双跑（Parallel Validation）裁决

| 问题 | 裁决 |
|---|---|
| 是否允许短时间双跑 | ✅ **允许**，但**双跑的定义是"双读单写"**，不是"双写" |
| 两个 n8n 可否同时读取生产邮箱 | ✅ **可以**（只读语义下是幂等行为）。前提：两侧均**不设置 `\Seen`**、不做任何写/删除/移动 |
| 数据是否允许双写 | ❌ **禁止**。ClickHouse 为单侧权威：迁移期为 ECS，切换后为集群。**不做双向复制、不做 ClickHouse 集群** |
| 如何防止重复发送 | **同一时刻只有一个日报生产者**。迁移期：平台侧发送目标被限制为**测试群**，生产群由 ECS 独占 → 物理隔离，不可能重复。切换后：ECS 调度停用 |
| 如何防止重复 Mark Read | 两侧均只读；**未读计数**作为一等监控指标，任一侧出现下降即告警并立即中止双跑 |
| 如何防止 ClickHouse 污染 | 两侧各自独立 ClickHouse 实例；平台侧只写自己的库。迁移期禁止任何跨实例写入 |
| 如何防止"双跑污染业务判断" | 所有比对结论以**逐项数字比对报告**为准，不接受"看起来一样" |
| 双跑时长 | **连续 3 个自然日**三窗口全绿（若出现任一不一致，计时归零重跑） |

> **明确否定的做法：** 让两个 n8n 都执行完整链路（都入库、都出图、都发钉钉），然后依赖"人工检查"避免重复。这不具备确定性，明确禁止。

### 7.2 邮箱归属（原"待决策项"的收口）

原方案曾把"平台是否拥有邮箱"列为需业务决策的开放项。**在 ADR-001 下该问题不再开放：**

> **切换后，生产邮箱的日常读取权归属 Kubernetes 内的 n8n。** ECS 停止调度并保留凭据至 V0.1 结束（作为回退条件的一部分）。

迁移期（P1–P8）的邮箱读取为**双读**，其安全性由"只读语义 + 未读计数监控 + 单写者发送隔离"三重保证。

## 8. Cutover 与 Rollback

### 8.1 Cutover Gate（全部满足才允许切换）

| # | Gate 项 | 判定标准 | 证据 |
|---|---|---|---|
| G1 | 数据一致 | 当天 / 近 6 周 / 近 6 月三窗口与 ECS **逐项完全一致** | Data Parity Report |
| G2 | 图片一致 | 出图内容/字段/时间标注一致 | 图片比对记录 |
| G3 | 业务流程一致 | 每日链路成功率、顺序、失败中止语义与 ECS 一致 | 3 日双跑记录 |
| G4 | 邮件读取行为一致 | 未读计数不变；无 `\Seen`；无写/删除；不触碰指定邮箱 | 未读计数曲线 + 邮箱审计 |
| G5 | DingTalk 行为一致 | 测试群收到且格式正确；生产群零污染；群 ID 来自 Secret | 发送记录 + Secret 检查 |
| G6 | 备份成功 | etcd + ClickHouse + 配置 + raw archive + n8n 工作流备份全部成功 | 备份任务记录 |
| G7 | 恢复测试成功 | ClickHouse 数据恢复演练成功且数字一致 | Restore Report |
| G8 | 监控正常 | 节点/Pod/业务指标（含数据新鲜度）可见 | 监控截图/API 证据 |
| G9 | 日志正常 | Pod 日志、审计日志可检索 | 检索记录 |
| G10 | 告警正常 | 人为触发至少 3 类告警均送达 DingTalk | 告警记录 |
| G11 | 回退路径验证成功 | **回退演练已真实执行并成功**；ECS 侧可运行性与数据完整性已验证 | Rollback Rehearsal Report |
| G12 | 切换与回退 Runbook 就绪 | 明确操作步骤、责任人、时限、判据 | Runbook 文档 |

### 8.2 切换执行（单写者切换，可在维护窗口内完成）

```text
T-1d  冻结变更：平台侧与业务侧均停止非必要变更
T0    确认最后一次双跑三窗口全绿 + 全部 Gate 通过
T1    停用 ECS 侧 DA-SOC 调度（保证单写者）
T2    将集群 n8n 的发送目标由「测试群」切换为「生产群」（仅修改 Secret 引用，不修改工作流）
T3    启用集群侧 DA-SOC 调度（对齐原生产时间）
T4    观察首个完整日报：收到图 + 数字与 ECS 前一日基线一致
T5    记录切换完成；ECS 转入冷备
```

> **关键设计：** 切换**不修改任何业务逻辑**，只做两件事 —— ① 转移调度权（单写者）；② 切换发送目标（Secret 中的群 ID）。这使切换成为**可逆的最小操作**，而不是一次"业务迁移"。

### 8.3 必须立即回退的触发条件

| # | 触发条件 | 回退动作 |
|---|---|---|
| R1 | 三窗口任一数字与基线不一致，且原因不可解释 | 立即回退 |
| R2 | `/archive` 行为异常（成功但未入库、失败但继续、部分写入） | 立即回退 |
| R3 | `/render` 行为异常（出图失败、图内容错误、字段缺失） | 立即回退 |
| R4 | ClickHouse 数据异常（重复、缺失、乱码、时区偏移） | 立即回退 |
| R5 | 邮件读取异常（未读计数下降、收到写/删除迹象、读到非目标邮件） | **立即回退 + 立即人工核查邮箱** |
| R6 | DingTalk 发送异常（发到错误群、重复发送、发送失败且无告警） | 立即回退 |
| R7 | 备份异常（连续 2 次失败或备份过期 > 26h） | 立即回退 |
| R8 | 出现**不可解释的数据缺失**（当日无数据但源邮件存在） | 立即回退 |
| R9 | 当日日报在业务时限内未产出 | 立即回退并按补发流程处理 |

### 8.4 回退执行（目标 ≤ 30 分钟）

```text
1. 停用集群侧 DA-SOC 调度（恢复单写者）
2. 将集群 n8n 发送目标改回测试群（防止误发生产群）
3. 启用 ECS 侧原调度（ECS 的镜像、数据、配置、凭据均保持可用）
4. 触发/等待 ECS 产出当日日报，确认数字正确
5. 记录事件（Incident Record）：触发条件、时间线、影响、根因、改进项
6. 在集群侧修复问题 → 重新走 P6–P8 验证 → 重新过 Gate
```

**回退的可行性依据：** ECS 侧在切换期间**只被停用、未被修改**（镜像未删、数据未动、配置未改、凭据保留），因此回退是"重新启用"，而不是"重建"。

### 8.5 ECS 退役判据（V0.1 结束前评审）

同时满足以下条件才可退役 ECS 侧 DA-SOC：

1. 切换后稳定运行 ≥ 30 天，无 R1–R9 类事件；
2. 至少完成一次**真实**的 ClickHouse 恢复演练与一次集群级恢复演练；
3. 集群侧 raw archive 与 ClickHouse 数据经比对确认完整；
4. 业务方书面确认日报连续正确；
5. 退役方案本身经过批准（含历史数据最终归置）。

## 9. 被否决的方案及原因

| 被否决做法 | 原因 |
|---|---|
| V0.1 只纳管 ECS / 只做影子环境 / 延后到 V0.2 承载 | 与 ADR-001 直接冲突；且无法验证平台承载能力与 AI-Native 可运维性 |
| 两个 n8n 同时执行完整日报链路（双写双发） | 非确定性：无法保证不重复发送、不重复标已读、不污染数据。**明确禁止** |
| ClickHouse 双写 / 双向复制 / 分布式 ClickHouse | ADR-004 明确不做分布式存储；双写会立即引入数据一致性与冲突解决问题，收益为零 |
| 直接迁移（先停 ECS 再在集群启动） | 单点时刻无回退；DA-SOC 是每日一次机会的确定产物，不可接受 |
| 保留 host network 以便"少改" | 违反平台安全红线；且会绕过 NetworkPolicy，使边界失效 |
| 修改 DA-SOC 业务实现以适配平台（如改写 SQL、换编排工具） | 违反"平台不得改变业务语义"；路径 A 明确禁止 |
| 由平台代管"补数/重跑发送"能力 | 违反 LLM 不参与出数、archive 失败即熔断等业务纪律；会把平台变成业务逻辑的一部分 |

## 10. 后果与影响

### 正面

1. V0.1 真正完成"承载业务"这一核心目标，验收具备实质意义；
2. 切换是"最小可逆操作"（调度权 + 群 ID），回退成本极低且已演练；
3. 平台承载完整业务链路后，AI-Native 运维才有真实对象可观测、可验证；
4. 单一权威数据源（单写者）避免了一致性复杂度。

### 负面 / 代价（必须显式接受）

1. 迁移期需要**双份资源与人力**（ECS 与集群同时存在）；
2. 双跑需连续 3 天人工/半自动比对，且必须在业务时间窗内完成；
3. 单副本单节点 ClickHouse → **RPO=24h**（见 ADR-004），这是有意识接受的取舍；
4. 切换当日存在一次"只有一次机会"的风险窗口，由 Gate 与已演练的回退路径对冲；
5. 平台对 DA-SOC 的可用性责任显著上升（从"不影响"变为"负责承载"）。

### 后续必须完成的事项

1. 迁移与回退 Runbook（含责任人与时限）；
2. 数据一致性比对方法（脚本或清单）与 Data Parity Report 模板；
3. 未读计数监控与告警（邮箱纪律的可验证化）；
4. 数据新鲜度告警（当日无数据即告警）；
5. ClickHouse writer / read-only 双账号落地；
6. ECS 退役评审（V0.1 结束前）。
