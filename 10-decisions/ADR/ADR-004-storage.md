# ADR-004：存储架构 —— local PV / local-path，不使用分布式存储

| 项 | 内容 |
|---|---|
| **状态** | Accepted（原则接受，本次裁决确认实现形态与恢复语义） |
| **相关** | ADR-001（DA-SOC 承载）、ADR-003（Harbor）、ADR-006（Backup） |

---

## 1. 决策

> **玄武云盾 V0.1 采用"节点本地存储 + 集群外备份目标"的存储架构：Kubernetes 侧仅提供 `local-path`（动态供给）与 `local-static`（ClickHouse 专用，`Retain`）两个 StorageClass；不部署 Ceph、Rook、Longhorn、GlusterFS、分布式 MinIO，也不部署分布式 ClickHouse。**
>
> **核心交换：用"可重建 + 可恢复 + 可重放"替代"跨节点漂移与在线高可用"。**

同时裁定：

1. **ClickHouse 使用 `local-static` 静态 PV（`persistentVolumeReclaimPolicy: Retain`），固定绑定到一个指定 Worker 节点**，不使用动态供给（防止误删 PVC 导致数据丢失）。
2. **raw archive 采用分层**：业务运行窗口（≥90 天）在集群 PVC；**全量历史归档到集群外 MinIO**。
3. **明确接受代价：节点/数据盘故障时，ClickHouse 最多丢失 24 小时数据（RPO=24h）。** 该取舍由本 ADR 显式接受，并由备份 + 恢复演练 + 源数据可重放共同对冲。
4. **不得以"更企业级"为理由在 V0.1 引入分布式存储。**
5. **共享存储（NFS）仅作为备份归档与应急中转的可选目标，不作为业务数据的主存储。**

---

## 2. 背景

### 2.1 候选方案共识（5/5 一致）

| 方案 | 结论 | 关键表述 |
|---|---|---|
| codebuddy | 不做分布式存储 | "DA-SOC v0.1 **零共享存储需求**"；给出 V0.2+ 触发条件 |
| codex | 不做分布式存储 | "当前主要风险是正确恢复，而非跨节点在线复制" |
| cursor | 不做分布式存储 | "DA-SOC 单副本即可；分布式存储显著增加故障面与运维成本" |
| dsh | 不做分布式存储 | 与 Longhorn/Ceph 的复杂度-收益比不成立 |
| kimi | 不做分布式存储 | "任何为『企业级』引入分布式存储的提案应被 Red-Team 直接否决" |

**这是本次综合评审中一致性最高的决策之一。** 分歧仅在实现细节（StorageClass 命名、Retain 策略、raw archive 归属），本次裁决统一如下。

### 2.2 先回答"DA-SOC 真正需要什么"

| 需求 | 真实要求 | 结论 |
|---|---|---|
| ClickHouse 数据 | 单节点本地高速盘；数据 GB–百 GB 级；**可从源邮件重放重建** | 本地 PV 足够 |
| ClickHouse 备份 | 需要可恢复快照，且恢复必须被演练 | 原生 `BACKUP` → 集群外 S3（MinIO） |
| n8n 工作流与执行历史 | 10 GiB 级；工作流 JSON 已在 Git 可重建 | `local-path` 动态卷 |
| raw archive | 追加写、可回补读；是"可重放"的物理依据 | 集群内窗口 PVC + 集群外全量 MinIO |
| 平台组件卷（Prom/Loki/Harbor） | 可重建或已备份 | `local-path` |
| 共享读写需求 | **无**（三个组件都是单 Pod 读写） | **不需要共享存储** |

**关键判断：** DA-SOC v0.1 没有任何跨节点共享读写需求，也没有节点故障自动漂移的 SLA 要求。引入分布式存储所要解决的问题，在 V0.1 并不存在；而它引入的故障模式（OSD/MON/PG 或 engine/replica/instance-manager、脑裂、数据均衡、性能调优）却是"无专职云原生运维团队"最难以可靠诊断的。

## 3. 存储清单（V0.1 全部）

| StorageClass | Provisioner | 回收策略 | 用途 | 说明 |
|---|---|---|---|---|
| `local-path` | local-path-provisioner | Delete | 默认 SC；n8n、Prometheus、Loki、Harbor（集群外不适用）、MinIO（集群外不适用） | 数据可重建或已有备份 |
| `local-static` | `kubernetes.io/no-provisioner` | **Retain** | **ClickHouse 专用** | 手工创建 PV + 节点亲和；`Retain` 保证误删 PVC 不丢数据 |

| 持久化对象 | 卷 | 规格 | 落点 | 备份 |
|---|---|---|---|---|
| ClickHouse 数据 | `local-static` PV | 300 GiB | `xw-wk-01`（业务 Worker） | 每日原生 BACKUP → MinIO，保留 30 天 |
| raw archive（窗口） | `local-path` PVC | 100 GiB | `xw-wk-01` | 每日文件级备份 → MinIO，保留 30 天；全量历史另存 MinIO |
| n8n 数据（含执行历史） | `local-path` PVC | 20 GiB | `xw-wk-01` | Velero 每日，保留 14 天 |
| Prometheus TSDB | `local-path` PVC | 100 GiB | `xw-wk-02` | 不备份（可丢失，V0.1 非恢复目标） |
| Loki 数据 | `local-path` PVC | 50 GiB | `xw-wk-02` | 不备份（同上） |
| MinIO（备份目标，集群外） | 宿主机数据盘 | ≥ 1.5 TiB | `xw-bak-01` | 自身纳入文件级备份 + 独立故障域 |

**数据放置原则：** 业务数据（ClickHouse、raw、n8n）集中在 `xw-wk-01`；平台可重建数据（Prom/Loki）在 `xw-wk-02`。这样节点故障的影响面清晰：`xw-wk-01` 故障影响业务，`xw-wk-02` 故障只影响观测。

---

## 4. 必须认真解决的四个故障场景

"不做分布式存储"不等于"不处理存储故障"。以下四类必须给出明确处置，并纳入 Runbook 与演练：

### 4.1 节点故障（`xw-wk-01` 宕机）

| 项 | 处置 |
|---|---|
| 影响 | ClickHouse / n8n / raw 不可用 → **当日日报无法产出** |
| 检测 | NodeNotReady 告警（A1/A2）、业务数据新鲜度告警（A12） |
| 恢复 | ① 优先恢复原节点（本地 PV 数据仍在盘上）；② 若节点不可恢复：重建节点 → 恢复 ClickHouse（BACKUP 或 POP3 重放）→ 恢复 PVC 数据 → 恢复 raw |
| RTO | ≤ 4 小时 |
| RPO | ≤ 24 小时（ClickHouse）；raw ≤ 24 小时 |
| 演练 | 节点故障演练（关机 → 观察 → 恢复）；ClickHouse 恢复演练 |

**为什么"优先恢复原节点"：** 这是 local PV 架构的关键操作纪律。节点盘上的数据是主数据，重建节点会引入不必要的数据重建成本。Runbook 必须明确"先尽力恢复原节点，再考虑重建"。

### 4.2 数据盘故障（ClickHouse 数据盘物理损坏）

| 项 | 处置 |
|---|---|
| 影响 | 该节点 ClickHouse 数据全部丢失 |
| 恢复 | ① 更换磁盘 → 重建 PV 目录 → `RESTORE` 最新备份（RPO ≤ 24h）；② 若备份不可用 → **POP3 一次性回补重放**（补齐历史窗口），再跑日常增量 |
| 前提 | 备份与"可重放"必须都经过演练 |
| 演练 | R3 ClickHouse 数据恢复演练（必须真实完成） |

### 4.3 PVC 数据恢复（误删 PVC / 命名空间）

| 项 | 处置 |
|---|---|
| ClickHouse | `Retain` 策略保证 PV 不被删除；重新绑定即可 |
| 其他 PVC | Velero restore（含 `node-agent` 文件系统备份） |
| 命名空间整体误删 | Velero 命名空间级 restore + Git re-apply |
| 演练 | R1 Velero 恢复演练（必须真实完成） |

### 4.4 整集群重建

| 项 | 处置 |
|---|---|
| 路径 | Git 定义态 → 重建集群 → Harbor（集群外，存活）提供镜像 → Velero 恢复资源与卷数据 → ClickHouse RESTORE → 验证数字 |
| RTO | ≤ 8 小时（阶段目标） |
| 前提 | ① Git 完整（含 kubeadm 配置、清单、Helm values）；② Harbor 独立于集群（ADR-003）；③ 备份在集群外（本 ADR） |

> **这三条前提正是 ADR-003 与 ADR-004 相互配合的地方：Harbor 与备份都不在集群故障域内，集群重建才是可行的。** 若把 Harbor 或备份放进集群，"可重建"就只是口号。

## 5. RPO / RTO（本 ADR 明确声明）

| 场景 | RPO | RTO |
|---|---|---|
| 单 Pod / Deployment 误删 | 0（Git 定义） | ≤ 15 分钟 |
| `da-soc` 命名空间整体误删 | ≤ 24h（数据）/ 0（定义） | ≤ 2 小时 |
| 单个 Worker 节点故障 | 0（优先恢复原节点） | ≤ 4 小时 |
| ClickHouse 数据盘损坏 | ≤ 24 小时 | ≤ 4 小时 |
| 控制面全失（etcd 损坏） | ≤ 30 分钟（etcd 每 30 分钟快照） | ≤ 4 小时 |
| 整集群重建 | ≤ 24 小时 | ≤ 8 小时 |
| Harbor 故障（集群外） | 0（镜像可重建 / tar 兜底） | ≤ 4 小时 |

**诚实声明：** RPO=24h（ClickHouse）是**有意识接受的取舍**，不是遗漏。接受理由：① 数据可从邮件源重放；② 对"每日一次的批处理业务"，丢失一天数据的业务影响远小于引入分布式存储带来的运维风险；③ 备份 + 演练使其可恢复。**若业务方认为 24h 不可接受，必须重新裁决本 ADR**（见 §7）。

## 6. 被否决的方案及原因

| 被否决 | 原因 |
|---|---|
| Ceph / Rook | 运维复杂度最高（MON/OSD/PG/CRUSH + 网络调优），故障模式最难被 Agent 可靠诊断；V0.1 无共享存储需求 |
| Longhorn | 最小可用形态需 3 副本 + instance-manager，占用多个 Worker 的 CPU/内存；引入"存储引擎自身故障"这一新故障域；收益（跨节点漂移）在 V0.1 无需求 |
| GlusterFS / 分布式 MinIO | 同上，且组件生命周期更复杂 |
| 分布式 ClickHouse / 多副本事务数据库 | V0.1 单业务、GB 级数据、每日批处理，无水平扩展或在线 HA 需求 |
| NFS 作为业务主存储 | 引入网络存储单点与性能不确定性；仅作备份归档/应急中转 |
| 为"未来业务"提前建设共享存储 | 违反"不为 V1.0 提前建设"原则；未来需求未知，提前抽象必然错误 |
| 直接把正在写入的 PVC 目录做文件级复制当作备份 | 无法保证一致性（"不能只复制正在写入的 PVC"）；必须用原生 BACKUP 或快照语义 |

---

## 7. 重新评估的触发条件（V0.2+）

满足**任一**条件时，重新裁决存储架构：

1. 出现**跨节点共享读写**的真实业务需求；
2. 出现**节点故障自动漂移**的 SLA 要求（业务方明确不接受 4 小时 RTO）；
3. Worker 节点数 ≥ 5，且本地存储运维成本显著上升；
4. 单业务数据量从 GB 级进入 TB 级，本地盘容量或性能无法满足；
5. 业务方明确**不接受 RPO=24h**（此时必须重新裁决，而不是默认维持）。

---

## 8. 后果与影响

**正面：** 零分布式存储运维；故障模式简单可诊断；备份与恢复路径清晰；集群可从 Git 重建；Agent 可完全操作（PVC/PV/StorageClass 都是标准 API）。

**负面 / 代价：**

1. **Pod 不能跨节点漂移** —— 节点故障需"恢复"而非"迁移"，RTO 依赖 Runbook 熟练度；
2. **RPO=24h（ClickHouse）** —— 见 §5 声明；
3. 磁盘容量需人工规划（无自动扩容）；
4. 无 CSI 快照能力（Velero 使用文件系统备份路径，成本更高但可用）。

**对后续版本的影响：** V0.2/V0.5 按 §7 触发条件重新评估；在此之前，"引入分布式存储"的提案应被直接否决，除非同时给出可量化的触发条件证据。
